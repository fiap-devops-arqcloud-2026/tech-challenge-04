Plano de ação em etapas

Oito etapas em sequência, porque você implementa sozinho. A regra que organiza a ordem: tudo o que dá para provar sem cluster é provado antes de ligar o cluster. Cada hora de EKS gasta crédito da conta; cada hora no Compose não gasta nada. As marcas local e AWS dizem onde a etapa roda.

E0 — Fundação local AWS só leitura

Objetivo
Código no repositório certo, contas criadas, estado da AWS conhecido.
Tarefas
  • Inventário somente leitura: clusters EKS, repositórios ECR, conteúdo do bucket de estado e terraform state list nas três camadas. Nada de apply.
  • Trazer a Fase 3 para o 04 com histórico e trocar os pontos acoplados ao nome do repositório (ver inventário).
  • Criar as contas: New Relic (license key), PagerDuty (serviço com integração Events API v2), Slack (workspace, canal, webhook de entrada) e o token do GitHub.
  • Conferir o crédito AWS restante e o fim do suporte padrão do EKS 1.34 na região.
Pronto quando
O CI roda verde na dev do 04, as chaves estão guardadas fora do Git e você sabe o que existe na conta.
Requisitos
prepara REQ-OBR-01 a 05, 12, 17 e 18

E1 — Instrumentação local

Objetivo
Um trace com os cinco serviços, fila incluída, visível no New Relic — sem cluster.
Tarefas
  • Go primeiro (auth, evaluation): é onde está o trabalho manual — contexto de ponta a ponta e span da SQS.
  • Python depois (flag, targeting, analytics): instrumentação automática, mais o consumidor da fila.
  • Um Collector local no Compose, exportando para o console e para o New Relic. O Compose de integração já emula SQS e DynamoDB com o moto.
Pronto quando
Um GET /evaluate no Compose aparece no New Relic como um único trace passando pelos cinco serviços, e o Service Map mostra os cinco conectados.
Requisitos
REQ-OBR-13, 14, 15, 21 · REQ-BON-02

E2 — Plataforma no cluster AWS

Objetivo
A base da Fase 3 rodando de novo, agora a partir do repositório 04, com capacidade para a stack nova.
Tarefas
  • Terraform: terceiro nó, namespace observability, Secrets novos.
  • apply nas três camadas; merge dev → main para publicar as imagens instrumentadas.
Pronto quando
Os cinco pods estão Running com as imagens novas e o ArgoCD mostra Synced.
Requisitos
REQ-OBR-01 a 05

E3 — Stack de observabilidade por GitOps AWS

Objetivo
Prometheus, Loki, Grafana e as duas releases do Collector instaladas pelo ArgoCD a partir de gitops/observability/.
Tarefas
  • As 4 Applications Helm e a Application observability; enableRemoteWriteReceiver: true; Alertmanager desligado.
  • Variáveis OTEL_* nos ConfigMaps apontando para o gateway.
  • Conferir: nome real da métrica do spanmetrics; HPA contra selfHeal; se a sincronização das CRDs do chart falhar, testar a opção ServerSideApply=true na Application.
Pronto quando
O Prometheus tem as métricas do spanmetrics, o Loki tem logs de todos os namespaces e o New Relic recebe traces vindos do cluster.
Requisitos
REQ-OBR-06, 07, 08, 09, 11, 20

E4 — Dashboard e alerta AWS

Objetivo
O dashboard com os três painéis e a regra de alerta chegando aos três destinos.
Tarefas
  • Dashboard e regra como ConfigMaps versionados; contact points de PagerDuty, Slack e webhook; política de notificação agrupando por serviço.
  • Decidir janela e duração (for) da regra.
Pronto quando
Um erro provocado leva a regra a Firing, o PagerDuty abre incidente, o Slack recebe a mensagem e o GitHub recebe o repository_dispatch.
Requisitos
REQ-OBR-10, 16, 17, 18

E5 — Self-Healing AWS

Objetivo
O ciclo completo sem intervenção humana.
Tarefas
  • Role própria com confiança OIDC restrita ao repositório; access entry com AmazonEKSEditPolicy limitada ao namespace togglemaster.
  • Workflow e script com filtro de status, allowlist e cooldown.
  • O mecanismo da falha proposital (ver perguntas em aberto).
Pronto quando
O ciclo roda três vezes seguidas sem intervenção, e um segundo disparo dentro do cooldown é recusado.
Requisitos
REQ-OBR-19, 22

Perguntas em aberto

Coisas que o código e o enunciado não respondem. Nenhuma bloqueia a E0 ou a E1.

  1. Quanto crédito AWS resta? Aparece em Billing → Credits. Define quantas horas de cluster o plano pode gastar.
  2. Estado do Terraform depois da migração: o 04 assume o mesmo bucket e as mesmas chaves, ou começa em chaves novas? Depende do inventário da E0 — se a base da Fase 3 ainda existe, chaves novas colidiriam nos nomes dos repositórios ECR.
  3. Qual falha provocar no vídeo? (a) Um endpoint administrativo no flag que liga um estado de erro só na memória: o reinício cura de verdade. (b) Parar o banco do flag, exemplo da p. 6: mostra a tentativa, mas o reinício não resolve. (c) Outra ideia sua.
  4. Qual serviço o self-healing reinicia? Uma falha no flag gera erro no flag (500) e no evaluation (502), e a regra por serviço dispara para os dois. A allowlist define se o workflow reinicia só a origem ou ambos.
  5. O grupo continua? Você implementa sozinho, mas o relatório pede nomes, RMs e usernames (REQ-OBR-33) e o PDF diz "em princípio" em grupo (Q-03).
  6. Grafana, Prometheus e Loki também no Compose? Mais trabalho na semana 3, menos horas de cluster nas semanas 4 e 5 para desenhar o dashboard.
  7. Registrar o prazo no README de requisitos? A dúvida Q-05 diz que o PDF não informa data; posso anotar que você informou 2026-11-17, deixando claro que a fonte é você, não o enunciado.
