Em miúdos: o material tem cinco partes numeradas no sumário — “O que vem por aí”, “Hands on”, “Saiba mais”, “O que você viu nesta aula?” e “Referências”. Infrastructure Agent: o coletor em nível de sistema operacional

Em miúdos: é um serviço que fica ligado no servidor observando a máquina de fora das aplicações. Ele não precisa que o código seja alterado para enxergar consumo de CPU ou memória.

Tecnicamente: a aula o descreve como um daemon leve e de alta performance, executado em servidores físicos, máquinas virtuais e instâncias na nuvem, cujo objetivo principal é coletar dados em nível de sistema operacional. Atua como sensor local; os dados coletados são empacotados, enviados de forma segura para a plataforma, processados e armazenados no New Relic Database (NRDB), ficando disponíveis para visualização, consulta e alerta. A arquitetura foi pensada para baixo overhead, de modo que o monitoramento não prejudique as aplicações observadas. O agent também é o ponto de coleta das integrações on-host, que estendem o monitoramento a serviços específicos como bancos de dados (MySQL, PostgreSQL) e web servers (NGINX, Apache), e é a peça-chave do monitoramento de contêineres, por detectar e coletar métricas de ambientes Docker e Kubernetes.

Fonte: APM — Aula 7, p. 5–6.

Instalação e configuração: o que a aula recomenda

Em miúdos: instala-se pelo gerenciador de pacotes do sistema e edita-se um arquivo de configuração. Só uma linha é realmente obrigatória: a chave de licença.

Tecnicamente: a aula indica os gerenciadores nativos — APT para Debian/Ubuntu e YUM para RHEL/CentOS — como método preferido, por facilitar instalação inicial, atualizações e manutenção. O processo tem três etapas-chave: adicionar o repositório oficial da New Relic à lista de fontes de software, importar a chave GPG para garantir a autenticidade dos pacotes e instalar o pacote com sudo apt-get install newrelic-infra ou sudo yum install newrelic-infra. A configuração principal fica em newrelic-infra.yml, localizado em /etc/.

Inventário e metadados automáticos

Em miúdos: além de medir o consumo de recursos, o agent anota como a máquina está configurada: que pacotes tem, que serviços rodam, que versão do sistema usa. E guarda o histórico das mudanças.

Tecnicamente: ao contrário das métricas de série temporal, coletadas a cada poucos segundos, os dados de inventário são coletados em intervalos maiores e apenas quando ocorrem mudanças, o que cria um registro histórico das alterações de configuração do host. Quando uma mudança é detectada — por exemplo, um pacote instalado ou um serviço iniciado — o agent gera um evento do tipo InfrastructureEvent, registrado no NRDB. A aula lista quatro famílias de dados de inventário:

  • Pacotes de Software: todos os pacotes instalados, com nomes e versões (exemplo do material: openssh-server 7.6p1).
  • Serviços do Sistema: status dos serviços gerenciados pelo systemd ou outro init system (exemplos: sshd, nginx).
  • Configurações do Kernel: parâmetros de configuração do kernel do Linux.
  • Informações do Sistema: versão do sistema operacional, hostname e tipo de instância em ambientes de nuvem como AWS EC2.

Esses metadados são automaticamente associados a todas as métricas coletadas: ao olhar o uso de CPU de um host, vê-se também a versão do kernel, o tipo de instância EC2 e o restante do contexto. A aula justifica o recurso com três perguntas que passam a ser respondíveis — uso médio de CPU em todos os hosts com determinada versão do NGINX; quais hosts de produção ainda executam uma versão vulnerável do OpenSSL; se houve alteração de configuração num host pouco antes de um pico de latência. É essa correlação entre performance e configuração que, segundo o material, transforma a ferramenta de monitoramento em plataforma de observabilidade.

Fonte: APM — Aula 7, p. 10–11.

Auto-discovery do runtime Docker

Em miúdos: contêineres nascem e morrem o tempo todo, então configurar o monitoramento de cada um seria inviável. O agent olha o socket do Docker, descobre o que está rodando e começa a medir sozinho.

Tecnicamente: a aula parte do problema — contêineres são efêmeros, têm ciclos de vida curtos e são criados e destruídos em grande escala e alta velocidade — e conclui que uma abordagem que exija configuração manual por contêiner é inviável. Quando o agent roda num host com runtime de contêiner compatível, como o Docker, ele detecta a presença do runtime e monitora todos os contêineres em execução sem configuração adicional. O mecanismo tem quatro passos:

  1. Detecção do socketO agent procura o socket do Docker, por padrão em /var/run/docker.sock — a API pela qual o cliente Docker e outras ferramentas falam com o daemon.
  2. Coleta de metadadosConectado ao daemon, usa a API do Docker para listar os contêineres em execução e obter ID, nome, imagem utilizada, labels e portas mapeadas.
  3. Coleta de métricasUsa os mecanismos do próprio kernel Linux (cgroups) para medir com precisão CPU, memória e I/O de rede e disco de cada contêiner isoladamente.
  4. Geração de eventos ContainerSampleAgrega e envia os dados como eventos ContainerSample, cada um um snapshot das métricas e metadados de um contêiner num dado momento, gerados a cada 15 segundos por padrão.

A conclusão da aula é que basta garantir o Infrastructure Agent instalado no host subjacente, sem instrumentar cada contêiner individualmente, e que essa funcionalidade é a base do monitoramento de contêineres no New Relic.

Fonte: APM — Aula 7, p. 14–16.

Infra Agent rodando como contêiner

Em miúdos: quando não se pode instalar nada no sistema operacional do host, o próprio agent vira um contêiner — mas precisa de permissões especiais para enxergar para fora de si mesmo.

Tecnicamente: a aula cita dois cenários que justificam a alternativa: sistemas operacionais otimizados para contêineres (RancherOS, CoreOS ou Bottlerocket da AWS) e políticas de segurança que restringem a instalação de software no host. Para eles, a New Relic oferece uma imagem Docker oficial do Infrastructure Agent. O modelo consiste em executar o contêiner do agent em modo privilegiado, dando acesso a informações e namespaces do host, de modo que ele colete métricas do host subjacente e dos demais contêineres — nas palavras do material, o agent “enxerga para fora” de seu próprio contêiner. As flags que quebram o isolamento padrão de forma controlada são estas.

Flag ou volumeO que concede, segundo a aula
--privileged ou --cap-add=SYS_PTRACEPermissões elevadas no host, necessárias para inspecionar processos e coletar certos tipos de métricas.
--pid=hostCompartilha o namespace de PID do host, para o agent ver e listar todos os processos da máquina, e não apenas o seu.
--network=hostConecta o contêiner diretamente à pilha de rede do host, permitindo coleta precisa de métricas de rede.
-v "/:/host:ro"Monta o sistema de arquivos raiz do host como volume somente leitura em /host, dando acesso a arquivos de sistema como os de /proc e /sys para métricas de disco, memória e sistema.
-v "/var/run/docker.sock:/var/run/docker.sock"Monta o socket do Docker do host dentro do contêiner — a mesma técnica do auto-discovery, para listar e inspecionar outros contêineres.
--cgroupns=hostAparece no comando do hands-on (p. 21) e é citada em bloco na análise do comando (p. 21) entre as flags que concedem permissões; a parte teórica das p. 19–20 não a descreve individualmente.

A aula conclui que executar o agent como contêiner é uma maneira flexível e declarativa de gerenciar o monitoramento, alinhada a infraestrutura como código, e que a configuração pode vir por variáveis de ambiente no docker run ou, de forma mais robusta, por uma imagem customizada que herda da oficial e inclui um newrelic-infra.yml personalizado.

Fonte: APM — Aula 7, p. 19–20.

Modelo de dados: o evento SystemSample

Em miúdos: a cada poucos segundos o agent tira uma “foto” do sistema e manda como um registro único, com dezenas de campos e todo o contexto do host junto.

Tecnicamente: a aula chama o SystemSample de pedra angular do monitoramento de hosts: um snapshot abrangente do estado de saúde e performance do sistema operacional num dado momento, coletado por padrão a cada 5 segundos. Seus atributos se agrupam em quatro categorias, além dos metadados.

CategoriaAtributos citadosComo a aula lê o dado
CPUcpuPercent, decomposto em cpuUserPercent, cpuSystemPercent, cpuIoWaitPercent e cpuStealPercentA decomposição diagnostica a natureza da carga: cpuIoWaitPercent alto sugere CPU ociosa aguardando disco, ou seja, gargalo de I/O e não de processamento.
MemóriamemoryTotalBytes, memoryUsedBytes, memoryFreeBytes, memoryCachedBytesAjuda a identificar vazamentos de memória ou a necessidade de provisionar mais RAM.
DiscodiskUsedPercent, diskFreeBytesVisão geral do espaço; performance de I/O (leitura/escrita por segundo) fica no evento separado StorageSample.
RedereceiveBytesPerSecond, transmitBytesPerSecondThroughput de entrada e saída do host; o detalhe por interface fica no NetworkSample.
Metadadoshostname, kernelVersion, awsRegion, ec2InstanceType e os atributos customizados do newrelic-infra.ymlEnriquecem cada evento; é a combinação de métricas de alta frequência com metadados ricos que permite a análise contextualizada.

Modelo de dados: o evento ContainerSample

Em miúdos: o mesmo tipo de “foto”, mas de cada contêiner, e com um campo que revela se o contêiner está sendo freado por falta de CPU.

Tecnicamente: o ContainerSample é gerado sempre que o agent detecta um ambiente de contêineres num host monitorado, com um evento por contêiner em execução a cada 15 segundos por padrão. A aula diz que sua estrutura responde a perguntas como qual contêiner consome mais CPU, se a aplicação sofre com limitação de memória (throttling) e qual imagem está associada a um pico de tráfego de rede.

CategoriaAtributos citadosComo a aula lê o dado
Identificação e metadadoscontainerId (o ID longo), containerName, image (o ID da imagem) e imageName (nome e tag, ex.: fiap-apm-api:latest)Identificam unicamente o contêiner; em Kubernetes há enriquecimento com podName, deploymentName e namespace.
CPUcpuPercent, cpuCoresPercent, cpuThrottleTimeMscpuPercent é o uso em relação ao total de CPUs do host e cpuCoresPercent em relação aos cores alocados ao contêiner; cpuThrottleTimeMs indica o tempo em que o kernel “congelou” o contêiner por exceder seus limites — sinal claro de subprovisionamento.
MemóriamemoryUsageBytes, memoryCacheBytes, memoryResidentSizeBytes, memoryUsageLimitBytesO limite configurado permite calcular facilmente o percentual de uso em relação a ele.
RedenetworkRxBytes, networkTxBytes, networkRxErrors, networkTxErrorsBytes recebidos e transmitidos e erros, que ajudam a diagnosticar conectividade.
DiscodiskReadBytes, diskWriteBytesThroughput de leitura e escrita do contêiner no sistema de arquivos.

O fechamento do tópico afirma que o ContainerSample transforma a natureza efêmera e isolada dos contêineres em telemetria estruturada e acionável, e que consultá-lo via NRQL sustenta dashboards de saúde do ambiente, alertas sobre o consumo de um serviço específico e análises de capacidade para otimizar a alocação de recursos no cluster.

Transposição para o ToggleMaster: se o grupo escolher New Relic em REQ-OBR-12, o que esta aula ensina e continua valendo em EKS é o modelo de dados — ContainerSample por contêiner, atributos customizados como chave de agrupamento, NRQL com FACET e TIMESERIES — e a disciplina de padronizar nomes de serviço antes de montar qualquer painel (SUG-03). O que não se transpõe é o caminho de instalação: apt-get numa VM e docker run com --privileged não cabem num cluster entregue por GitOps, e o enunciado da Fase 4 pede o OTel Collector central como roteador de métricas, logs e traces (REQ-OBR-11), não o Infrastructure Agent. Esta caixa é elaboração do guia, não da aula.

Qual evento responde “quanto de memória este contêiner está usando” e com que frequência ele chega?

ContainerSample, com o atributo memoryUsageBytes; a aula diz que um evento por contêiner em execução é capturado a cada 15 segundos por padrão. Fonte: APM — Aula 7, p. 24.

Por que o agent containerizado precisa de --pid=host e do socket do Docker?

O namespace de PID do host permite que ele veja e liste todos os processos da máquina, não só o seu; o socket montado permite falar com o daemon do Docker para listar e inspecionar os outros contêineres — a mesma técnica do auto-discovery. Fonte: APM — Aula 7, p. 19–20.

Para memorizar: um agent no host, dois eventos — SystemSample a cada 5 s para a máquina, ContainerSample a cada 15 s para cada contêiner; o Docker é descoberto pelo socket e medido por cgroups; metadados e custom_attributes são o que torna o NRQL útil; e o que a aula promete em dashboards e alertas ela não chega a demonstrar.
